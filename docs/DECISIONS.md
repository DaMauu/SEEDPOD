# 决策记录

每条只写三件事：定了什么、为什么、代价是什么。改主意就在下面追加新条目，不删旧的。

## D1 前端保持无构建静态页面

定了：`pta/web` 直接用 index.html + app.js + app.css，不引入打包器。
为什么：本机单机使用，改一行刷新就见效，出问题用浏览器就能查。
代价：没有模块系统，靠文件内分块和命名约定维持秩序；文件变大后必须靠重构而不是工具解决。

## D2 用 hash 路由

定了：`#dashboard`、`#sites` 这类，刷新和直接打开都能定位。
为什么：静态文件不需要服务端重写规则。
代价：地址栏不好看，SEO 无意义（也不需要）。

## D3 后端用 Node 单进程 + SQLite

定了：一个进程、一个数据库文件，不开 Redis、不搞队列中间件。
为什么：单机、单用户量级，运维成本为零；备份就是拷一个文件。
代价：并发上限低，任务靠进程内调度；将来多机再换。

## D4 请求层的硬底线写在服务端

定了：并发、最小间隔、退避、熔断、审计写死后端；前端只能改速度，越界拒绝保存。
为什么：账号被限的代价远大于抓得慢，底线不能被界面参数绕过。
代价：用户想极限速度时会被拒，需要接受「慢就是稳」。

## D5 正则只用于标题规则

定了：正则只出现在发布侧标题匹配，限 200 字，编译失败退回纯文本。
为什么：正则参与请求层会带来不可预期的行为和超时。
代价：复杂匹配做不到，需要更强的表达时要另开 DSL。

## D6 检查先于功能

定了：`pta/checks/run.cmd` 全绿才允许提交。
为什么：改需求最容易悄悄弄坏旧功能，没有断言就只能靠人肉点。
代价：加功能前先想清楚怎么断言，前期会慢一点。

## D7 分类映射逐站配置

定了：每个站点一张「站点分类 → 库内分类」表，不做全局统一表。
为什么：各站分类命名和粒度都不同，统一表一定会猜错。
代价：站多时配置量线性增长，需要「按名字自动猜」来降低负担。
