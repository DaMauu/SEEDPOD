# SEEDPOD 架构说明

这份文档先回答三个问题：这东西是什么、各部分怎么协作、为什么这么定。代码可以照着它写，AI 也可以照着它改。

## 一、一句话定位

把原盘转载站点的「抓取 → 查重 → 准备 → 发布」做成一个可控流水线：源站只负责发现资源，目标站只负责发布，中间的资料补全、质检、限速、审计都在自己手里。

## 二、现状与目标

| | 现在 | 目标 |
| --- | --- | --- |
| 前端 | 纯静态页面，假数据，`pta/web`，无构建 | 同一套页面接真数据，保留无构建 |
| 后端 | 极简服务已能起（health / 配置读写 / 日志流 / 静态托管） | Node 单进程服务，加 SQLite 与执行器 |
| 数据 | 浏览器 localStorage | SQLite（配置、站点、任务、审计） |
| 抓取/发布 | 界面演示 | 服务端执行器 + qB 连接器 |
| 检查 | `pta/checks` 15 条断言 + 交互审计 | 同一套，加后端接口契约测试 |

写代码时先看这张表：前端可以继续演进，但别把业务逻辑写进页面；后端从零开始，按第三节分层写。

## 三、分层

```
浏览器（panel SPA）
   │  HTTP/JSON + SSE
   ▼
API 层  ── 鉴权、参数校验、错误格式
   │
   ▼
服务层  ── 任务编排：抓取、查重、准备、发布
   │
   ├── 站点适配器（NexusPHP / UNIT3D / Gazelle / 自建）
   ├── 请求调度器（令牌桶、单站冷却、熔断、审计）
   ├── 资料补全（TMDB、豆瓣网页、豆影）
   └── 下载器连接器（qBittorrent Web API）
   │
   ▼
存储层  ── SQLite：配置、站点、资源、任务、请求日志
```

- 面板层只管展示和交互，不判断业务规则；限速、重试、阈值全部在服务端。
- 站点适配器是唯一允许写「站点差异」的地方。新增一种架构只加一个适配器文件，不改服务层。
- 请求调度器是所有对外请求的唯一出口，任何模块都不许自己发请求。

## 四、数据流

1. 调度器按站点间隔触发抓取，适配器翻列表页、取详情页，产出候选资源。
2. 判定（是否原盘、是否禁转、是否重复）在服务层完成，规则来自配置。
3. 通过判定的资源落库，进入准备队列：补简介、抓截图、校验 BDInfo。
4. 准备完成进待审核；人工或自动通过后由发布器发到目标站。
5. 每一步都写审计记录：时间、站点、动作、结果、耗时。

## 五、数据模型（最小集）

| 表 | 关键字段 |
| --- | --- |
| site | host、name、arch、url、enabled、login_state、interval、daily_cap |
| cat_map | site_host、site_cat、lib_cat |
| resource | id、site_host、title、year、res、size、tmdb_id、state |
| publish_task | resource_id、target_host、state、attempt、last_error |
| request_log | ts、site_host、path、status、elapsed_ms、reason |
| config | scope（sys/user/site）、key、value |

## 六、配置分三层

- 系统层：写死，只读。并发 1、单站最小间隔 8 秒、失败退避、4xx 熔断、审计全开。
- 用户层：只开放速度类参数，有区间，越界拒绝保存。
  - 测试模式（默认）：间隔 30–120 秒，默认 60 秒；单站每日 20 条、全站 100 条。按人手点速度跑，用来验证流程。
  - 正式模式：间隔 8–120 秒；单站每日上限受站规三分之三零头保护，最多到站规的 1/3。
- 站点层：单站覆盖，优先级高于用户层，但不能突破系统层。

规则匹配用结构化字段加关键词；正则只允许出现在「标题规则」里，限长 200 字，编译失败就退回纯文本。

## 七、风控（为什么这么定）

- 账号被限制的代价远大于抓慢一点，所以下限写死在服务端，前端只是展示。
- 单站每日上限再乘一次站规系数的三分之一，避免同一 IP 集中打一个站。
- 4xx 立即熔断 15 分钟并遵守 Retry-After，连续失败暂停该站而不是整体停摆。
- 每次请求可追溯：谁触发、打了哪、多久、什么结果。出问题先看审计，不靠猜。

## 八、扩展点

- 新站点架构：`adapters/<arch>.js`，实现 list、detail、login 三个方法。
- 新图床：`uploaders/<name>.js`，实现 upload(files) → urls。
- 新检查项：`checks/<name>.js`，返回 pass/fail 与原因，发布前统一跑。

## 九、怎么验证

- 前端：`pta/checks/run.sh`（Linux），23 条功能断言 + 全量交互审计；其中 5 条是 demo 期遗留，待前端搬迁时重写。
- 后端：`pta/checks/api-v2.js` 起临时 Fastify + SQLite 实例跑契约测试（15 条），断言状态码、错误码、筛选与凭据不回显；旧 `api.js` 标 legacy。
- 任何改动过不了检查就不提交，这是唯一硬门槛。

## 十、已知差距

- 前端 2400 行单文件、CSS 多层覆盖，需要一次搬家式重构，不加功能。
- 后端为零，接口契约见 `docs/API.md`，实现在契约冻结后开始。
- 登录态、qB 连接、调度循环都还没有实现。
