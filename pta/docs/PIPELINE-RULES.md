## 二、三个收敛方案

### 方案 A：三档预设 + 高级折叠（推荐先做）

- 顶部加一个「策略档位」：简洁 / 标准 / 严格。档位只改默认值，不锁死单项。
- 发布条件卡只留 9 条：发布到、分辨率、体积区间、发布前检查、必须有简介、必须带中字、主站已有同片、限制分发、不满足时。
- 其余 11 条进「高级」，默认收起；收起时也要能一眼看到「高级里有 11 项」。
- 简介卡只留 4 条：简介图片、图床、来源顺序、获取方式；11 条进高级。

效果：首屏可操作控件 67 → 约 24，高级用户点开仍是全量。
代价：`data.js` 每行加 `adv` 标记，`app.js` 渲染加折叠；不动后端。
风险：档位含义要写清楚，否则用户不知道「严格」多了什么。

### 方案 B：按决策顺序重排（不改数量）

- 第一屏「发不发」：发布到、分辨率、体积、简介、中字、BDInfo、截图数。
- 第二屏「怎么发」：标题与副标题、简介来源、发布字段。
- 第三屏「失败怎么办」：重试、暂停、通知，默认折叠。
- 每条说明从常驻小字改成悬浮提示，行高降一半。

效果：不改功能，只改信息层级；风险最低。
代价：纯前端重排，文案迁移；测试点少。

### 方案 C：场景向导（改动最大）

- 新手只看 3 个问题：发到哪个站 / 收什么片 / 失败怎么办。
- 其余全用默认，结束页生成「本次生效的 12 条规则」摘要。
- 老手可切回「完整模式」。

效果：外行也能配完；但和现有手风琴是两套交互。
代价：新增页面状态、回填逻辑、至少 3 个提交；需要前端汇总摘要，后端可不改。

### 推荐

先做 A，顺手把 B 的文案和层级带进去；C 等真有第二个用户再说。

## 四、验收标准

1. 发布条件卡首屏可操作控件 ≤ 10 个。
2. 折叠外的每个手风琴 ≤ 8 行。
3. 1280 / 768 / 390 三个宽度无横向滚动。
4. 旧配置按字段名回填，值不变（`config.json` 兼容）。
5. `RULES-TREE.md` 与 `data.js` 一致，`gen-rules-tree.js` 无 diff。
6. 改前改后各截一张图，放在提交说明里对比。
