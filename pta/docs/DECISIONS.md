# 决策记录

每条只写三件事：定了什么、为什么、代价是什么。改主意就在下面追加新条目，不删旧的。

> 2026-11-16 起：早期条目里的 `app.js`、零依赖、无构建等是当时状态；当前以 `AGENTS.md` 和最新条目（D16/D17）为准。

## D1 前端保持无构建静态页面（已由 D17 取代）

定了：`pta/web` 直接用 index.html + app.js + app.css，不引入打包器。
为什么：本机单机使用，改一行刷新就见效，出问题用浏览器就能查。
代价：没有模块系统，靠文件内分块和命名约定维持秩序；文件变大后必须靠重构而不是工具解决。

## D2 用 hash 路由

定了：`#dashboard`、`#sites` 这类，刷新和直接打开都能定位。
为什么：静态文件不需要服务端重写规则。
代价：地址栏不好看，SEO 无意义（也不需要）。

## D3 后端用 Node 单进程 + SQLite

定了：一个进程、一个数据库文件，不开 Redis、不搞队列中间件。
为什么：单机、单用户量级，运维成本为零；备份就是拷一个文件。
代价：并发上限低，任务靠进程内调度；将来多机再换。

## D4 请求层的硬底线写在服务端

定了：并发、最小间隔、退避、熔断、审计写死后端；前端只能改速度，越界拒绝保存。
为什么：账号被限的代价远大于抓得慢，底线不能被界面参数绕过。
代价：用户想极限速度时会被拒，需要接受「慢就是稳」。

## D5 正则只用于标题规则

定了：正则只出现在发布侧标题匹配，限 200 字，编译失败退回纯文本。
为什么：正则参与请求层会带来不可预期的行为和超时。
代价：复杂匹配做不到，需要更强的表达时要另开 DSL。

## D6 检查先于功能

定了：`pta/checks/run.sh` 全绿才允许提交。
为什么：改需求最容易悄悄弄坏旧功能，没有断言就只能靠人肉点。
代价：加功能前先想清楚怎么断言，前期会慢一点。

## D7 分类映射逐站配置

定了：每个站点一张「站点分类 → 库内分类」表，不做全局统一表。
为什么：各站分类命名和粒度都不同，统一表一定会猜错。
代价：站多时配置量线性增长，需要「按名字自动猜」来降低负担。

## 2026-11-10 站点凭据怎么存

- 站点账号密码与 2FA 密钥只存密文：AES-256-GCM，密钥来自 `PTA_SECRET` 或 `data/.secret`（0600，自动生成）
- 接口永不回显明文，只回 `hasUser / hasPass / hasTotp`
- 登录自检必须由用户点击触发，同一站 60 秒一次；不做后台轮询、不做批量探测
- TOTP 自己算（`server/totp.js`），不引第三方库，按 RFC 4226/6238 的官方向量写死断言

## 2026-11-10 站点登录只保留 cookie

- 站点侧只用 cookie：不存账号密码、不算 2FA，导入一次就能用；过期就重新导入
- 账号密码 + 2FA 的代码与接口已删除（`server/totp.js`、`login-test`），避免留一条用不到又要维护的路径
- 面板自己的登录不受影响：仍然是 `PTA_USER` / `PTA_PASS` + HttpOnly 会话 cookie
- cookie 由本机浏览器直接导入（`scripts/import-cookies.js` 读 CDP），不让人手抄；
  传输走 ssh 到服务器后由 `scripts/load-cookies.js` 用服务器自己的密钥加密落盘，明文临时文件立即删掉
- 两条路径都只存密文，接口只回 `hasPass / hasTotp / hasCookie`

## D8 生产后端固定 Node + Fastify + SQLite（2026-11-14）

定了：唯一生产后端是 `pta/server/app-fastify.js`，Fastify 5 + `node:sqlite`，数据在 `data/seedpod.db`；旧 `app.js` 已删除。
为什么：搬迁已在 v0.7.35 完成，systemd 与健康检查都指向 v2；再维护两套必然分叉。
代价：新机器要装 fastify 依赖；旧单文件后端不再享受新功能。

## D9 前端固定 Vue 3，无构建（2026-11-14）

定了：Vue 3 通过本地 `vue.global.prod.js` 引入，页面仍是 `index.html + app.js + app.css`，不引入打包器。
为什么：改一行刷新就见效，排障不用看构建产物；单机面板不需要工程化。
代价：没有单文件组件与模块系统，大文件靠命名约定和分块维持。

## D10 最终交付必须能 Docker 部署（2026-11-14）

定了：功能完成后以 Docker 镜像 + compose 交付，数据卷挂 `/data`，端口 8080。
为什么：换机器、备份、回滚都简单，不依赖宿主 Node 版本。
代价：镜像构建要维护 Dockerfile 与依赖锁定；Dockerfile 已对齐 v2（两阶段构建）。

## D11 当前前端是 demo，定稿后整体搬迁（2026-11-14，已完成，由 D17 取代）

定了：`pta/web` 现在这一版是前端 demo，用来验证交互与流程；前端定稿后按目标架构整体搬迁一次，不在 demo 上继续堆结构。
目标架构：后端 Node + Fastify + SQLite（v2，已就位），前端 Vue，交付 Docker。
为什么：先把界面和流程跑通，再一次性把结构做正，避免边验证边重构两头耽误。
代价：demo 阶段会有临时代码与重复样式，搬迁时集中清理；前端是否引入构建工具（Vite / SFC）在搬迁前单独写进决策，当前保持无构建。

## D13 检查入口以 Linux 的 run.sh 为准（2026-11-14）

定了：`pta/checks/run.sh` 是主要检查入口，`run.sh` 只保留给 Windows 上的聊天环境备用。
为什么：开发与部署都在 Linux，浏览器用自带 Chromium（新 headless，支持下载），不再依赖 Windows 的 Edge。
代价：Windows 上跑检查要自己保证 Node 与浏览器依赖；Linux 首次要 `npm ci` 和 `npx playwright install chromium`。

## D14 演示账号与线上密码分离（2026-11-14）

定了：`AUTH_DEMO` 只用于 `file://` 演示模式，值与线上 `PTA_PASS` 无关；线上只走 `POST /api/login`。
为什么：真实密码曾被写进前端与检查脚本，仓库和 git 历史都可能泄露。
代价：demo 模式要用 `demo-pass` 登录；线上密码需要轮换一次（旧值已进历史）。

## D15 上传表单识别只走手动单次 GET（2026-11-16）

定了：站点抽屉的“从目标站识别”必须由用户点击并确认，只读目标站上传页，每次 1 个 GET，不提交、不重试；必须有已保存 cookie 和站点定义；同一站 60 秒冷却；域名和 base 不一致时拒绝，避免 cookie 外泄。识别失败保留字段表和 JSON 手工编辑。
为什么：用户不想手改上传 JSON，但面板不能自行探测真实站。
代价：首次识别需要站点定义里有上传路径、识别页路径和 cookie；`formPath` 留空会回退到提交路径。进程重启会重置冷却时间。测试用 `pta/fixtures/upload-form.html` + 本地 mock，不碰真实站。

## D24 页面主题与窄屏布局归页面（2026-11-17）

定了：日志页黑绿终端主题、日志行窄屏两行布局这类页面专属视觉，放 `Logs.vue` 的 `<style scoped>`；共用模块只留外壳、通用响应式和共享组件。
为什么：主题和行布局只服务一个页面，留在全局会继续制造跨页覆盖和死选择器。
代价：页面 SFC 会变大；迁完后仍要用 1280/768/390 验收，避免主题规则挡住共用组件。

## D23 页面 scoped 里的子组件样式用 `:deep`（2026-11-17）

定了：页面 SFC 的 `<style scoped>` 只锁页面根和页面自带元素；遇到子组件内部（如 Nodes 抽屉、RuleControl 的 input/switch/chip），用 `.page-root :deep(.child)`，不把子组件基础样式复制进页面。共享组件的基础规则继续放全局。
为什么：scoped 属性只加到本组件元素，子组件内部没有页面的 `data-v`；不写 `:deep` 会静默失效。
代价：`:deep` 选择器要限定在页面根下，避免泄漏；每次迁移都要在浏览器里点数、看开关/芯片尺寸。

## D22 质量审计固定进检查（2026-11-17）

定了：`pta/scripts/audit-quality.js` 固定进 `pta/checks/run.sh`，按代码、功能、编写、逻辑、简洁度、复用率、质量七个维度打分，评级为优质 / 平衡 / 勉强 / 差。支持全库、单文件、单功能、单项目。全库用 `pta/quality-baseline.json` 防回退；单文件/功能没有基线时，出现「差」即失败。改动后先在对应 scope 看发现清单，再跑全量。
为什么：功能检查只能证明“能跑”，不能及时暴露代码膨胀、重复、逻辑缺口和文档漂移；审计把这些变成每次提交都能看到的信号。
代价：审计是静态启发式，不是绝对真理；不能为了分数删检查/删文档；基线只允许在确认真实提升后更新。

## D21 不在 scoped 里用 `:global(...)` 加后代（2026-11-17）

定了：SFC `<style scoped>` 里需要页面外层 `.view[data-view="..."]` 布局时，只写单选择器 `:global(.view[...])`；不要写 `:global(.view[...]) .child`，Vue 编译会把后代丢掉，`[hidden]` 也可能被吞。页面内部元素直接在 scoped 里写，不依赖外层 global 前缀。
为什么：Sites 迁移时 `:global(.view[data-view="sites"])[hidden]` 被编译成 `.view[data-view=sites]{display:none!important}`，整个站点页被隐藏。
代价：外层布局规则只能是最小集，页面内部样式靠自身选择器保证作用域。

## D20 页面样式逐页迁 SFC scoped（2026-11-16）

定了：共用样式只留 `src/styles/` 的 base / shell / components / responsive / dock；页面专属规则迁进对应 SFC 的 `<style scoped>`；页面最外层 `.view[data-view="..."]` 布局用 `:global`；一次迁一页，迁完删除对应全局页面模块。每页验收：构建、smoke 21/21、全量检查、1280/768/390（Dashboard 加 1440）视觉、升版本、部署、更新文档。
为什么：减少全局选择器和覆盖链，页面样式跟页面走。
代价：scoped 会加属性选择器、改变特异性；每页都要视觉验收，不能一次全迁。

补充（2026-11-17）：Vite 产物里 SFC 的 scoped CSS 排在 `src/styles/` 之前，同特异性的 `:global(.view[data-view=...])` 会被 05/07 的全局规则覆盖。页面外层 `.view` 的布局和响应式覆盖实际留在 `src/styles/`（如 `09-responsive-pages.css`），SFC 只放页面内元素；要用 `:global` 必须提高特异性并在 1280/768/390 实测。

## D19 CSS 语义清理只做安全删除（2026-11-16）

定了：CSS 去重只删“被后续同选择器、同媒体上下文完全覆盖”的规则；只在相邻同选择器之间合并；只删规则内同属性同重要性的重复声明。不跨规则移动声明，不按覆盖率整块删，不改选择器。
为什么：这份样式是追加式演进的，跨规则移动声明会改变级联结果；完全覆盖删除和相邻合并可以静态证明安全。
代价：能清掉的重复有限（本次 -2,920 字节）；真正的结构重组仍需逐页迁 `<style scoped>`，风险更高，单独做。

## D18 站点基础清单进 SQLite（2026-11-16）

定了：v1 `data/sites-data.local.js` 的 305 个基础站迁入 SQLite `sites` 表；`/api/sites` 只读 SQLite，`base:true` 的站点禁止删除。旧 JS 与 8 个 v1 JSON 只留在 `data/_v1-backup-20261116`（0600），v2 不读；`library.json` / `site-search.local.json` / `site-status.json` 仍是 v2 文件数据。
为什么：站点清单是运行数据，v1 JS 读取是最后一处运行时 v1 依赖；SQLite 已经是配置、队列、凭据的唯一事实源。
代价：旧安装升级要跑一次 `pta/scripts/migrate-sites-js.js`；基础站删除保护要靠数据里的 `base:true`。迁移脚本和冒烟断言已覆盖。

## D16 站点包随程序发，密钥放部署环境（2026-11-16）

定了：站点包是数据文件，跟程序一起发布；用户安装/升级面板或 Docker 镜像即可，不单独下载、不导入。仓库里只放 AES-256-GCM 密文 `pta/pack/site-pack.enc`，密钥只放部署环境变量 `PTA_SITE_PACK_KEY`，安装时配置一次；缺密钥时回退私有 `data/` 站点定义并提示，不崩溃。私有 `data/site-defs` / `data/site-pack.json` 优先覆盖内置包。
为什么：站点 URL、站名、分类和上传字段是站点差异，必须预存才能自动化；但明文进仓库会泄露站点清单。
代价：部署多一个环境变量；密钥轮换要重新加密；内置包更新跟程序版本走。站点包不含 cookie/密码/账号/IP，也不授予站点权限。详见 `pta/docs/SITE-PACK.md`。

## D17 v2 共用样式进构建链（2026-11-16）

定了：共用样式放 `pta/web-src/src/styles/` 模块，`index.css` 为入口，由 `src/main.js` 导入，Vite 打包并哈希；2026-11-16 已拆成 12 个按级联顺序的模块；字体放 `src/assets/fonts/`，logo 放 `src/assets/whale.png`，`public/` 只留 favicon/icon。删除手工 `<link rel="stylesheet" href="/assets/app.css">` 和 CSS 指纹插件。
为什么：`public/assets/app.css` 是 v1/demo 资产路径，Cloudflare 还会缓存 4 小时；进构建链后文件名带哈希，发布即换 URL。
代价：CSS 改动会改构建哈希；页面级 `<style scoped>` 拆分仍需逐页做，当前先完成“v2 共用版”。D1/D11 里“无构建、直接 app.css”是历史记录，以本条为准。
