name: Code Review
description: 审查 diff、提交或 PR：找 bug、回归、安全、数据一致性和测试缺口；提交前检查。只审不改。
---

## 何时用
用户说「审一下」「看看这次改动」「提交前检查」「code review」，或准备合并/发版前。

## 步骤
1. 读 `AGENTS.md`、`pta/docs/QUALITY.md`，先看 `git diff --stat` 和完整 diff。
2. **先复述意图**：用一句话说清这次改动要解决什么；说不清就停下来问，不靠猜审。
3. 按顺序检查：正确性、边界条件、错误码/重试语义、幂等与重复提交、事务边界、权限与凭据、UI 冻结、测试缺口、命名与结构。
4. 需要时跑对应检查（`node pta/checks/<name>.js`），不要先改代码。
5. 每条问题给 `文件:行号`，先结论后原因；有作者解释的非显然选择，先认可理由再提替代方案。
6. 没发现问题也要说清看了哪些范围、跑了什么检查。

## 输出
- 阻塞：必须改，否则不能合并
- 重要：应该改，说明影响
- 建议：可以改，说明收益
- 疑问：需要作者确认
- 做得好的地方：具体到模式，不泛泛夸
- 结论：通过 / 修改后通过 / 需要讨论

## 禁止
- 不直接改代码（除非用户明确要求顺手修）。
- 不打印密钥、cookie、站点名/网址。
- 不把“风格偏好”写成阻塞；有 linter/formatter 的格式问题不手抠。
